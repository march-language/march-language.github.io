Capabilities: March’s Effect & Capability System

A capability is a compile-time record of what a piece of code may do to the world: print, read a file, open a socket, spawn a task, call C. In March every module declares the capabilities it uses with needs, the compiler traces every call graph to check that the declarations are true and complete, and main’s parameter bounds what the whole program may reach. The checks cost nothing at run time: a Cap(X) is a null pointer unless you attach a test dictionary to it. What a run may do is also limited while it runs: each capability operation is checked against the run-time authority, which --grant or MARCH_GRANT can narrow at launch, a scoped function needs clause narrows inside the function, and a restrict block narrows for one block. A program that uses none of them pays two global loads per operation.

Three checks do the work. The manifest check makes every module declare what it touches. The upper limit makes the build fail if any module’s emitted code, your dependencies included, reaches a capability it did not declare. The grant makes the build fail if the program as a whole reaches anything beyond what main’s signature allows. The first two verify that declarations are honest; the third is where March says no.

The same cap keyword also carries five behavioral promises (cap no_panic, cap no_alloc, cap no_extern, cap pure, cap deterministic), and the same Cap(X) type carries proof caps (this initialisation ran) and typestate (this handle is open). This page covers all of them, in the order you are likely to need them.

“Effect” on this page means something that touches the outside world, not the academic “effect system”. There are no algebraic effects, no effect handlers, and no user-defined effects with row-polymorphic inference. What exists is a fixed, closed lattice of IO and behavioral capabilities, checked by tracing which of them a function’s reachable call graph touches. A Cap(X) parameter is not an upper limit over what a function reaches (that would force every caller to thread capabilities it does not otherwise need); a function that wants a narrower limit than its module declares one in its header instead (Per-function bounds), which callers never have to satisfy. See The grant.

The problem they solve

In most languages, a function’s signature tells you what data flows in and out. It says nothing about what the function does to the world:

# Does this read a file? Call the network? Write to a database?
# You have to read the implementation to find out.
def compute_price(product_id: str) -> float:
    ...

That invisibility causes three recurring problems:

Accidental effects. A function you thought was pure secretly calls a logger, which opens a file, which fails in a read-only sandbox. You find out at runtime.

Unclear contracts. “Does this library write files at any point?” requires reading all the source. No amount of documentation substitutes for a machine-checked declaration.

Audit blind spots. Answering “which modules talk to the network?” in a large codebase means grepping and hoping, unless the compiler tracks it.

March’s capability system addresses all three. Effects appear in the type, and the compiler traces them through the call graph. Leaving out a capability declaration breaks the build, whether Cap(X) flows through a signature (a function, actor or extern parameter, or a transitive use) or a function body calls an IO builtin directly. A call routed through a stdlib wrapper (File.read rather than file_read) slips past that particular check, but not the system: the capability upper limit catches it. To audit what a dependency or a compiled binary actually possesses, rather than what a module declares, see Capability Audit.

mod Price do
  -- No `needs`, and every parameter here is an ordinary value — no `Cap(X)`
  -- anywhere in the signature. This module cannot be forced to declare a
  -- capability it doesn't have, and calling into it can never trigger a
  -- signature-level cap error.
  fn compute(base : Float, discount : Float) : Float do
    base * (1.0 - discount)
  end
end

IO permission caps

Every module that touches external resources declares needs:

mod Server do
  needs IO.Network

  fn listen(port : Int) : () do
    ...
  end
end

A module’s needs limits its own operations: a module whose code reaches for an IO operation it does not declare is rejected, naming exactly what is missing; see What the compiler tells you. A function never receives its authority as an argument: it uses the current authority, which main’s needs clause asks for and each operation checks (run-time authority). The stdlib-mediated route is covered by the upper limit.

Cap(IO.X) values were retired (object capabilities, phase 7b). Earlier releases passed Cap(IO.X) values between functions and narrowed them with cap_narrow; those values were erased at run time and granted nothing. A Cap(IO.X) type outside main’s parameters is now the error cap_param_retired, and cap_narrow and root_cap are errors too. forge fix removes such a parameter and the argument at each call.

Capability hierarchy

IO is the root. Sub-capabilities narrow what is allowed:

IO
├── IO.Console          — stdout/stderr (println, print)
├── IO.FileSystem
│   ├── IO.FileRead     — read files, list directories
│   └── IO.FileWrite    — write, delete, rename files/dirs
├── IO.Network
│   ├── IO.NetConnect   — outbound TCP
│   │   ├── IO.NetConnect.TLS  — encrypted transport (Tls.client_ctx, Tls.server_ctx)
│   │   ├── IO.Database — database connections (declaration-only; child of NetConnect)
│   │   └── IO.WebSocket — WebSocket connections (declaration-only: a WsSocket is a handle; child of NetConnect)
│   └── IO.NetListen    — bind + listen on a port
├── IO.Process          — env vars, child processes, process exit
├── IO.Clock            — wall clock (unix_time_ms, DateTime.now); monotonic time is ambient, see below
├── IO.Random           — CSPRNG (random_bytes, uuid_v4)
├── IO.Signal           — OS-signal watchers (Signal.watch/unwatch/raise)
├── IO.Spawn            — task spawning (task_spawn, task_spawn_link, …)
├── IO.Mut              — shared mutable state (Vault tables)
├── IO.Registry         — naming and finding actors by name (Actor.register/whereis/registered)
├── IO.Cluster          — attaching a session, starting or attaching a cluster node
├── IO.Telemetry        — telemetry/observability emission (declaration-only)
└── IO.Foreign          — calling unverified C (extern blocks)
    └── IO.Foreign.Blocking — blocking extern (spawns OS thread)

Actor.Introspect        — reaching actors you were not handed: Actor.introspect, Actor.pid_from_int
Actor.Debug             — reading another actor's state: Actor.debug

Actor.Introspect and Actor.Debug are roots of their own, outside IO: needs IO does not let a program inspect every actor’s state. A program that uses them asks for them in main’s request (fn main() needs IO.Console, Actor.Introspect do).

Monotonic time is ambient. sys_uptime_ms and its stdlib wrapper System.monotonic_time (milliseconds since the process started) are not gated by IO.Clock: they read elapsed time inside the process, not the wall clock, and gating them would break every timing caller granted only IO.Console. They are still a clock read, so cap pure and cap deterministic both reject them, called directly or through a stdlib wrapper (see Behavioral caps).

declaration-only (IO.Database, IO.Telemetry): the compiler accepts the needs as a surface-contract annotation but does not scan for specific builtins behind it (there is no dedicated builtin set to attribute to it). It makes the concern visible to callers; it is not enforced by a body scan the way the other capabilities are.

Declaring a capability is a compile-time claim. To see it become a runtime boundary (a compiled binary actually denying the syscalls a withheld capability gates), see OS-level enforcement, including the full capability-to-OS-primitive map.

This IO lattice is closed: every IO-rooted path in a needs declaration must appear in it. An unrecognized IO-rooted path (wrong case, a typo) or a bare leaf standing in for a real capability (needs Network instead of needs IO.Network) is a compile-time error with a did-you-mean suggestion, rather than being silently accepted and only surfacing later as a confusing “no function requires it” warning or an unrelated missing-needs error. Capability roots outside the IO lattice (e.g. needs Ffi, a dotted namespace like needs Db.Migrated, or an FFI extern’s Cap(LibC)) are intentionally not in this table and stay free-form. The one exception is a bare, single-segment name whose spelling collides with a real capability’s leaf case-insensitively: needs Network is rejected in favor of needs IO.Network, since that is almost always a real capability written without its IO. path rather than an actual FFI root. A dotted non-IO path is never subject to that check, even if its last segment happens to coincide with an IO capability’s leaf (needs MyLib.Clock, needs Vendor.Random): the dot makes it unambiguously its own namespace.

To run part of a program under less authority than the rest, wrap it in a restrict block:

fn start() : () do
  restrict IO.NetListen do
    Server.listen(8080)
  end
end

Choosing the right level

Use the narrowest capability that accurately describes what the code actually does. Narrower declarations make stronger claims; the compiler verifies them.

What the code does Declare
No external state, no I/O (no needs line: pure by declaration)
Print to stdout/stderr needs IO.Console
Read files or directories needs IO.FileRead
Write, delete, or rename files needs IO.FileWrite
Read and write files needs IO.FileSystem
Outbound TCP needs IO.NetConnect
Outbound HTTPS only, no plaintext TCP needs IO.NetConnect.TLS
WebSocket connections only needs IO.WebSocket
Accept inbound connections needs IO.NetListen
Vault tables (shared mutable state) needs IO.Mut
Spawn green tasks needs IO.Spawn
Wall clock or sleep needs IO.Clock
Random number generation needs IO.Random
Watch OS signals (Signal.watch) needs IO.Signal
Environment variables, child processes needs IO.Process
Calling C via extern needs IO.Foreign
Blocking C calls (OS threads) needs IO.Foreign + needs IO.Foreign.Blocking
Application entry point or top-level composition needs IO

In libraries, prefer narrow caps. A library that only reads config files should declare needs IO.FileRead, not needs IO. Callers can then hand it a read-only view, statically proving it cannot secretly write.

In entry points, needs IO is fine. The interesting precision lives in the libraries. Application main modules compose everything; they do not need to obsess over narrowing.

Propagation is demand-driven

An importer inherits only what it actually references. Importing a module costs the capabilities of the functions the importer references from it, not the imported module’s whole set: importing List to call map costs no capability even though List.pmap spawns tasks, and you owe needs IO.Spawn only if you actually reference pmap. Reference edges are free-variable edges, so a function passed as a value counts, and a capability reached only through a private helper still counts. It is computed per import site: two modules importing the same library can owe different capabilities.

The demand set is always a subset of the imported module’s declared needs: it filters that set and never adds to it. So this rule can only require less than the older module-granular rule, and no module that compiled under that rule can start failing because of it. One conservative case errs toward requiring more: an import whose target has not been analyzed yet, because the two modules import each other cyclically, falls back to the imported module’s whole declared set (the module topological sort tolerates cycles rather than rejecting them).

In user terms: a function that does no impure work beyond reading a module-level let that prints does owe IO.Console, and so does anything that imports it for that function.

How the closure is computed. The per-function transitive capability closure is caps(f) = own(f) ∪ ⋃ { caps(g) | g ∈ refs(f) }. The demand set comes from the import tracker’s per-reference record (ie_used_names, populated by record_use as it resolves each EVar). record_fn_caps records an own(...) entry for every declaration form that can hold an expression: DFn signatures, bodies and guards, default-argument expressions, actor handlers, DExterns, module-level DLet bodies, DInterface default-method bodies and DImpl method bodies. (The last four were added 2026-08-06, specs/progress/2026-08-06-record-fn-caps-misses-dlet-and-methods.md; before that a DFn reaching a capability exclusively through one of them had a silently truncated closure.) Keying is what makes a reference resolve to its entry:

  • a DLet is keyed like a DFn of the same name, for each name its pattern binds;
  • a DImpl method is keyed by TIR’s Iface$Ty.method mangling, and a DInterface default body by the parallel Iface$default.method. Neither can collide with a DFn (an ordinary qualified name never contains $), nor with another impl of the same method for a different type. The bare method name additionally becomes a dispatch node with an edge to each implementation (the union over them, the sound reading of a name whose target is chosen by type), emitted only when the module declares no DFn of that name, so a plain function’s identity is never absorbed. Without that guard, a module that legally declares an interface method with a default body and a top-level fn of the same name would have the pure fn silently inherit the default body’s capabilities on the hot-deploy manifest, which reads the own-caps table unfiltered;
  • a default argument is traversed directly when the module is undesugared, and via an alias from desugar’s arity-mangled f$N declarations onto the base name f on the production path (expand_defaults_decl moves the default into f$0’s body but leaves call sites saying f).

Because the demand set is filtered against the imported module’s declared needs, no addition to own(...) can make the import check stricter than the module-granular rule it replaced.

What the compiler tells you

An uncovered capability is a build-breaking ERROR (--check exits 1). The route by which it is uncovered does not change the severity. (Before 2026-08-06 a direct builtin call in a function body was only a warning.)

Transitive use, or extern. If an extern declares a capability, or you use a module and reference a function from it that needs a capability you have not declared:

$ march --check caller.march   # `use`s a module needing IO.Network, no `needs IO.Network` of its own
-- CAPABILITY --
Module `Caller` imports `Server` which requires `Cap(IO.Network)`, but `IO.Network` is not declared in `needs`.
help: add `needs IO.Network` to the module body.
$ echo $?
1

It is the functions you reference that count, not the imported module as a whole (Propagation is demand-driven).

A direct body call to an IO builtin is the same severity:

$ march --check reader.march   # fn slurp(path) do file_read(path) end — no needs
-- CAPABILITY -- `slurp` reads a file, but module `Reader` declares no `needs IO.FileRead`.
hint: add this to the module body —
        needs IO.FileRead
$ echo $?
1

The error points at the first call that needs the capability and names the code it is in and what it does: a function (`slurp` reads a file), an actor handler (the `Inc` handler of actor `Counter` prints) or a module-level let. It includes a machine-applicable fix, so forge fix will insert the needs line for you. Every offending capability in the module is collapsed into one diagnostic, not one per call site: a main that touches four undeclared capabilities gets a single error naming all four once (each other capability’s first use is a label), with one fix that inserts all four needs lines at once:

-- CAPABILITY -- `main` prints, but module `Main` declares no `needs IO.Console`; its code also reaches `IO.FileWrite`, `IO.Random`, `Time.Clock`.
hint: add these to the module body —
        needs IO.Console
        needs IO.FileWrite
        needs IO.Random
        needs Time.Clock

What this does and does not guarantee

The error above is easy to over-read. What it covers:

  • It catches a direct call to a capability builtin: file_read(p) (since ocap phase 4 only stdlib code can make one; a user program’s direct call is a stdlib_internal error).
  • It does not catch, on its own, the same operation routed through a stdlib wrapper: File.read(p). That call is invisible to this check. It is caught by the capability upper limit instead.
  • The complete check is the upper limit, which works on emitted code and therefore cannot be evaded by re-routing through a helper. It runs however the program is checked or run: --compile, --check, --check-json, march check (what forge check and forge build run), the interpreter, --jit, march test, the REPL (for a mod declared at the prompt) and the editor. Outside --compile the program is lowered on demand for it; the interpreter remembers a clean verdict until a source changes.

So needs is a mandatory, mechanically-verified manifest of the builtins a module calls directly, not, on its own, proof that a module cannot reach a capability. That proof comes from the upper-limit check. A program the compiler cannot build (one using an interpreter-only builtin such as App.stop) cannot be held to it outside --compile either: it runs with one cap_unchecked warning saying so, and --compile rejects it.

There is also a distinction hiding in the word “capability”: this check makes you declare what you touch. It does not make anyone grant it: needs is a self-declaration, and any module may write any needs line. IO builtins take no capability argument. The grant is where authority is bounded.

Capabilities are inferred from the call graph, not threaded through parameters

The compiler works out what a function touches by walking its call graph at compile time, the same closure computation the import check uses (caps(f) = own(f) ∪ ⋃ { caps(g) | g ∈ refs(f) }). It does not need the capability passed to it as a value to know that. (This is a different mechanism from the capability inference hints, which only suggest a missing needs line. The walk described here is the actual check, used everywhere on this page.)

log and log_error below take no Cap parameter at all, and the write still succeeds. The compiler follows the call graph down to File.write and finds that the module Logger declares needs IO.FileWrite:

mod Logger do
  needs IO.Console
  needs IO.FileWrite

  fn log(msg : String) : Unit do
    Authority.ignore(File.write("/var/log/app.log", msg))
  end

  fn log_error(msg : String) : Unit do
    log("ERROR: " ++ msg)
  end

  fn main() : Unit needs IO.Console, IO.FileWrite do
    log_error("disk full")
  end
end

This compiles as-is. Delete needs IO.FileWrite and it fails, not with a missing-parameter error but with the compiler naming the whole path:

`log` writes a file, but module `Logger` declares no `needs IO.FileWrite`.
...
reached from `main`: main → log_error → log

This differs from an object-capability language. In Wyvern, E, or Newspeak’s capability subset, authority exists only as a value: a function that never receives the write capability as a parameter verifiably cannot write. log there would need a signature like log(write : WriteCap, msg : String), and every caller above it would need to hold and forward that value.

March gives a coarser guarantee: not “this function received the authority as data” but “the compiler checked the module’s entire reachable call graph, however many private helpers deep, and none of it goes beyond what the module declared”. It is still mechanically checked (--check exits 1 on the deleted-needs version above).

Earlier releases also let IO capabilities flow as explicit Cap(X) values across module boundaries. Those values were erased at run time and granted nothing, so they were retired (object capabilities, phase 7b): narrowing is done with restrict and dependency grants, which the run time enforces, and a capability that is a value is a proof capability (below).

The capability upper limit: on by default

needs is an upper limit as well as a floor: the build fails if any module’s emitted code uses a capability that module did not declare. This is the default (since 2026-08-07); --no-cap-strict opts out, and --cap-strict is still accepted if you would rather say it explicitly.

$ march --compile -o app app.march
-- CAPABILITY ------------------------------------ dep.march

Module `HostileDep` uses `IO.FileRead` but does not declare `needs IO.FileRead`. [cap_ceiling]
help: add `needs IO.FileRead` to the module body.

1 capability ceiling violation(s). Every module's emitted code must stay
within its own `needs`.
Add the missing `needs` line to the module named above, or pass
`--no-cap-strict` to build without this check.

Three things make it stronger than the manifest checks above.

It covers every route to a capability. The check runs against the code the compiler is about to emit, not the surface syntax, so a direct builtin call, a call through a stdlib wrapper like File.write, and a builtin given out as a value all collapse into the same rule. Re-routing a call through a helper does not evade it. (The stdlib-mediated route produced no diagnostic at all before this shipped: the import check walks use declarations, and stdlib modules are ambiently available without one.)

It applies per module, including dependencies that never opted in. March dependencies ship as source, so the check runs on your build of their code. A dependency declaring only needs IO.Console with a helper that reads /etc/passwd fails your build. You do not need the publisher’s cooperation.

It fails closed. A capability the compiler cannot attribute to any module (reached only through an indirect call) is reported as a violation rather than passed, because that is exactly the route an attacker would use.

Because attribution charges a stdlib-mediated call to the calling module, the standard library’s own declarations are not involved: the module that called File.write is the one required to declare needs IO.FileWrite.

It is strict, and turning it on by default was a breaking change for code written before it: a module that reaches a capability through the stdlib has to say so, needs IO.Console most commonly. The compiler names the module and the capability, so each fix is one line. --no-cap-strict unblocks a build you do not want to migrate yet.

IO.Foreign is excluded: extern blocks are already an error when undeclared, and what linked C code does is outside the capability model entirely. The exclusion also covers first-party stdlib modules built on extern, such as Js.Dom, Js.Canvas and Js.Audio on --target js: those modules declare needs IO.Foreign themselves, so a module can call them without declaring any needs. Function-level needs () bounds and main’s grant still see the reach: a bounded function that calls Js.Dom.set_text gets [cap_bound], and a main granted only IO.Console gets [cap_grant_exceeded].

The same upper limit can be re-checked on a compiled binary with forge cap inspect --strict, which reads each module’s declared and measured capability sets out of the artifact.

The grant: main’s needs clause bounds the whole program

Everything above verifies the manifest: needs must be present and truthful, end to end. None of it stops anything: a module that declares needs IO.Network and exfiltrates passes every check, because the declaration is true. The grant is the point where March enforces a no.

main’s request is the program’s grant, and the program’s whole transitive capability closure must sit under it:

mod Report do
  needs IO.Console

  fn main() : () needs IO.Console do
    println("report done")
  end
end

needs IO.Console here is a machine-checked claim: this program (every helper, every stdlib call, every dependency main reaches) touches no resource beyond the console. Add a save helper that calls file_write anywhere in that closure and the build fails, naming the chain from main down to the frame that actually possesses the capability:

`main` is granted `needs IO.Console`, but the program reaches `IO.FileWrite`
(reached from `main`: main → save). The grant is a ceiling on the WHOLE program —
declaring `needs IO.FileWrite` does not raise it.
help: add `IO.FileWrite` to `main`'s request (its `needs` clause, or the module's
`needs` line when `main` has no clause), or request all of `IO`, or remove the use.

The help names the precise capability to add before the broad IO escape hatch, and the fix (forge fix applies it) adds exactly that: least privilege is the default the diagnostic steers you toward, not the widest grant.

Actors are inside the grant. A message handler’s body counts against main’s grant exactly like any other reachable code: an actor with a handler that calls file_write is charged the moment the program spawns it, so a program granted only IO.Console cannot smuggle a file write into a handler. An actor that is defined but never spawned costs no capability, the same dead-code-is-free rule the rest of the grant follows.

Three signatures, three meanings:

main signature grant
fn main() the module’s needs line; with no needs line, empty
fn main() needs () empty: a build error the moment the program’s closure reaches any capability; only a program that truly touches no IO compiles with it
fn main() needs IO.Console, IO.FileRead("/srv/") the clause, scopes included: the scopes are checked at run time (Run-time authority)
fn main() needs IO full IO
fn main(cap : Cap(IO.Console)) deprecated (warning deprecated_main_cap): the same request as needs IO.Console; removed in the next release

main’s request is its needs clause (together with the kinds of any deprecated Cap(...) parameters). With neither, it is the module’s needs line, so a program that prints needs only needs IO.Console in its module; needs () on main requests nothing. A program that reaches more than its request is a compile error naming the exact capability to add (`main` performs IO but declares no grant. The program reaches `IO.FileWrite`...), and forge fix writes it for you.

Two intentional edges:

  • IO.Foreign cannot sit under a narrow grant. What linked C code does is invisible to the capability lattice, so a program with a closure that reaches an extern block is not accepted under any grant narrower than IO, since the check will not certify a bound it cannot see.
  • The grant bounds what main reaches, not what the file contains. Dead code costs no capability, the same reachability the upper limit uses. (Its needs line is still required: the manifest checks are unchanged and orthogonal.)

The grant is needs’ missing complement: needs states what a module touches; the grant bounds what the program may. Sandbox ladder stages A/B/D are shipped (specs/2026-08-08-r1-no-ambient-io-design.md). Stage C, which made a Cap(X) parameter an upper limit over everything a function reaches, was removed because it forced every caller to thread capabilities it does not otherwise need; a declared bound (Per-function bounds) gives a function the same limit without involving its callers. A Cap(X) parameter is an authority marker at a module boundary; the checks are needs, the module upper limit, and main’s grant.

Per-role grants are the one other place a grant is checked. An @[endpoints] protocol can say role Ledger needs IO.FileWrite, IO.NetConnect; the role’s body then takes those capabilities as parameters, narrowed by the runner from main’s, and the same walk that bounds the program by main’s grant bounds the role’s code by its line, from each call of the role’s runner. A role’s grant must fit within main’s. See Choreography, including --dump-role-authority, the report of what a role can reach through references it is handed rather than through its own code.

Per-function bounds

A module’s needs bounds every function in it. A function can declare a narrower bound in its header, after the return type:

mod Report do
  needs IO.Console, IO.Clock

  fn log(msg : String) : Unit needs IO.Console do
    println(msg)
  end

  fn parse(body : String) : Int needs () do
    string_byte_length(body)
  end
end

needs () is the empty bound: the function performs no capability. Two checks apply:

  • The bound lies within the module. Every capability it names must be covered by the module’s needs (a parent covers its children: a module declaring IO.FileSystem admits a function bound of IO.FileRead). Otherwise cap_bound_needs.
  • The function lies within the bound. Everything the function reaches, through every function it calls, transitively, must be covered by the bound, the same reachability main’s grant is checked with. Otherwise cap_bound, naming the path to the capability: "`parse` is bounded by `needs ()`, but reaches `IO.Console` (via log → println)".

A bound has no effect on callers: calling a bounded function is the same as calling any other, and a caller stays bounded by its own module and main’s grant. Two cases are worth knowing:

  • Callbacks are charged to whoever supplies them. `fn apply(f : Int -> Int, x : Int)
    Int needs () do f(x) end is accepted: calling f` is charged to the caller that passed it, as everywhere else in the capability checks. A bound means “my own authority, plus whatever you hand me”.
  • Untraceable calls are refused. A body that calls a function value taken out of a record field, a list or a ref (a codec’s stored encoder, say) cannot be charged to anyone, so a bound narrower than all of IO is rejected (cap_bound) rather than certified. Pass the function in as a parameter or call it by name instead.

The bound may sit on any one clause of a multi-clause function, and covers all of them; two clauses declaring different bounds is a syntax error. Impl methods take bounds the same way. Local functions inside a body do not: their reach already counts toward the function that contains them. A function bound may carry scopes (needs IO.FileRead("/etc/myapp/")); the compiler checks its kinds as above, and the scopes are checked at run time only, against the target each operation is given (Run-time authority).

Interface methods take a bound too, after the method’s type, and it holds every impl of that method (and the interface’s default body) to it, including impls written in other modules:

interface Store(a) do
  fn get : (a, String) -> Option(String) needs IO.FileRead
  fn describe : a -> String needs ()
end

An impl method with no bound of its own is checked against the interface’s (cap_bound, naming the interface). One with its own bound may narrow the interface’s but not widen it (cap_bound_iface), and is then held to its own. An interface’s bound need not lie within its own module’s needs: it limits other modules’ impls, and each impl’s module still needs the capability itself. A violation reached only through another impl’s (a generic impl Store(List(a)) when Store(a) calling an impure impl Store(Disk), or a bounded function calling get) is reported once, at the impl that has it; once that impl is fixed, anything the caller reaches beyond its own bound is reported in turn. The four built-in interfaces are bounded by needs (); see Standard Interfaces.

No capability threading. A bound, on a function or an interface method, is a check made once where the bounded code is written. It is never part of a type and never carried by a when Iface(a) constraint, so no caller, generic function or signature has to declare anything because of it. A call through an interface is charged what the impls in the program actually reach, exactly as before.

Host and method scopes on IO.NetConnect

A module can narrow outbound network access to the hosts it may reach, and to the HTTP methods it may use on them:

mod Billing do                          -- your own code
  needs IO.NetConnect("api.stripe.com", methods(get, post))
end

mod Weather do                          -- wraps a dependency: read only
  needs IO.NetConnect("api.weather.test", methods(get), no_redirects)
end

Billing may reach only api.stripe.com, with GET or POST; Weather only api.weather.test, with GET, and never follows a redirect. Scopes are per module and per host: each module’s own needs lines decide.

Scope syntax. A host (example.com), a host and port (example.com:8443), any subdomain (*.example.com, which does not include example.com itself), or an IP literal, optionally followed by a path prefix (api.example.com/v1/weather/). No scheme or userinfo; host names are compared case-insensitively, paths case-sensitively.

Path prefixes match by whole segment: /v1/weather/ admits /v1/weather and /v1/weather/today, not /v1/weatherman; the query string never counts. A request path is judged only if every character is a plain path character (letters, digits and -._~!$&'()*+,=:@/; no ;, ?, #, space or control character), every % escape is well formed and does not decode to ., /, \, % or a control character, and it has no // and no . or .. segment. Anything else is refused outright rather than cleaned up, because a server may resolve it differently (or, with a CR/LF, read a second request). A literal prefix proves the host but not the path ("https://api.example.com/v1/weather/" ++ "../admin"), so under a path scope every request’s path is checked when it is sent, and the compiler reports the violations it can see. A path-scoped host admits no plain Socket.connect. A URL with no port uses its scheme’s default (80 or 443). Two options may follow, in either order: methods(...) with any of get, head, post, put, patch, delete, options, and no_redirects. Options alone mean any host: needs IO.NetConnect(methods(get)). Without methods(...) every method is allowed, and unscoped needs IO.NetConnect still means any host. Host scopes are accepted on IO.NetConnect only; it also bounds the TLS connections built on it. (IO.Mut and IO.Registry take name scopes instead.)

Scope syntax. The parenthesised scope takes several leading strings, then options: needs IO.Mut("a", "b"). An option may take a string argument as well as identifiers: needs IO.Registry(prefix("worker.")), or both, needs IO.Registry("logger", prefix("worker.")). Strings come first; once an option appears no further string may follow. Each encoding has one spelling: only methods(...) takes identifiers, every other option takes one string (prefix(w) is refused; write prefix("w")), a further name is a further string (there is no name(...) option), a scope string may not contain ;, and an empty first string may not be followed by more. Internally a scope is one string: each extra string becomes name=<s> and a string-argument option <option>=<s>, so IO.Mut("a", "b") is a;name=b. Which capabilities accept these forms, and what they mean, is set by the capability, not by the syntax.

What is checked, at compile time. In a scoped module, every network call must have a destination the compiler can see, inside the scope, with an allowed method; anything else fails the build. The check is fail-closed:

  • A literal URL, or a literal prefix that ends its host with / ("https://api.stripe.com/" ++ path), is checked against the scope. Without the / the rest could extend the host (".evil.test/"), so it is refused.
  • A URL from a parameter, a computed string, an operation on a socket the module was handed (Socket.write(s, ...), Tls.connect), or a call the compiler cannot follow is refused (cap_host_unproven).
  • The method comes from the call: HttpClient.get, HttpTransport.simple_get are GET, HttpClient.post POST, put_request PUT, delete DELETE. A plain Socket.connect shows no method, so it is allowed only to a host declared without methods(...).
  • The scope covers everything the module reaches, including calls into your other modules and dependencies. A helper that takes the URL as a parameter must say so with @[net_dest(url)], and is then checked to pass that parameter straight to the connection; its caller’s argument is checked against the caller’s scope. A helper with a fixed URL is checked as if its call were written in the scoped module. A helper in another module that makes HttpClient calls is refused for now (see below).
  • A function you hand in as a parameter is charged to whoever wrote it, as elsewhere on this page: a closure built in an unscoped main may be called by a scoped module.

What is checked, at run time. A redirect’s target and a request rewritten by client request steps are only known when the program runs. In a scoped module the compiler routes HttpClient calls through a variant that receives the module’s scope, and the client refuses, before connecting, a request outside it: HttpClient.OutOfScope(host), MethodRefused("POST host"), or under no_redirects RedirectRefused(host).

Limits. The compile-time check runs in every mode, like the upper limit: --compile, --check, march check, the interpreter, the REPL, the JIT and the editor. The run-time guard does not: a program run by the interpreter, the REPL or the JIT follows redirects freely, and only a compiled binary refuses a redirect or a step-rewritten host outside the scope. A message a scoped module sends to an actor it was handed (a pid from main) runs that actor’s handler under the handler’s module, not the sender’s: the same rule as a function handed in as a parameter. A scoped module that spawns a network-reaching actor itself is refused. They bound the name a module connects to, not the address it resolves to, and no OS sandbox enforces them: what C code reached through extern does is outside them, as it is outside every check here. A scoped module cannot call a stdlib server API (its socket handles are plain integers) or another module’s HttpClient-calling helper; move those to an unscoped module. A scope on main’s grant, which would bound dependencies’ own code as well, is planned (specs/todos/2026-11-09-host-scope-phase-2.md).

Refusals: capability operations return Result

Every capability operation can be refused by the authority the code runs under, and a refusal is a value, never a crash or a silent no-op (specs/2026-11-10-object-capability-design.md §15). So each one returns Result(T, CapError):

println("hi")                       -- Result((), CapError)
System.now_ms()                     -- Result(Int, CapError)
Process.env("HOME")                 -- Result(Option(String), CapError)
Task.async(fn () -> work())         -- Result(Task(a), CapError)
Vault.new("sessions")               -- Result(Vault(v), CapError)

An operation that already had its own failure keeps it, inside: the outer Result says whether the operation was permitted, the inner one whether it worked.

match File.read("/etc/motd") do
Ok(Ok(text))           -> text
Ok(Err(File.NotFound(_))) -> ""          -- the file is missing
Ok(Err(e))             -> panic(to_string(e))
Err(refused)           -> panic(Authority.describe(refused))
end

CapError(kind, target, limit, limit_scope) names the refused operation as a scope (IO.FileRead("/etc/motd")) and the limit that refused it (ByLaunch, ByFnNeeds(f), ByModNeeds(m), ByRestrict(at), ByGrant(pkg)) with that limit’s scope list. Authority.describe(e) renders it.

Using an operation only for its effect needs nothing: a statement’s result is discarded (println("hi") on its own line). Where the value is wanted, handle the refusal (match, let?), or write Authority.must(e), which takes the value and panics with the description on a refusal. Authority.ignore(e) discards a result where () is expected.

Code written before operations returned Result gets the diagnostic cap_result_unhandled with the fix: a line () after a unit result on its own line, Authority.ignore(...) around other unit results, Authority.must(...) around values. forge fix applies it to a project; forge fix --only cap_result_unhandled PATH... to files outside one.

What is not an operation: using what an operation opened. Vault.set on a table handle, reading or writing an open socket, the lines of an open file and a running process’s pipes need no authority and keep their types. Some stdlib helpers degrade instead of failing: List.pmap and friends compute sequentially when spawning is refused, IO.inspect and debug still return their argument, and the Logger drops a line or a timestamp.

Handles need no capability. A File.Handle, File.Dir, Socket, Listener, Udp.UdpSocket, Tls.TlsConn, WebSocket.WsSocket or Process is an unforgeable, reference-counted handle: user code gets one only from a checked open (File.open, Socket.connect, Socket.listen, Process.spawn_async, …), and the raw integer builtins under them (tcp_send_all, file_read_line, process_wait_proc, …) are internal to the standard library (stdlib_internal). Using a handle you hold is therefore not charged: a function bounded by needs () may read a File.Handle, write to a Socket or wait on a Process it was handed, and accept on a Listener; it may not open one. One caveat while a Vault’s element type is not part of its identity (Vault.open(name) lets the caller choose it): an opaque type over plain data, such as the cluster’s PeerRegistry.Fd, can be minted through a name-keyed Vault under the interpreter, and compiled code then fails at the stdlib’s match rather than refusing the open (specs/todos/2026-11-13-vault-element-type-not-identity.md); the handle boxes themselves cannot. A handle never leaves its node: a message type holding one cannot derive Json or go through Node.send (Clustering).

mod Wire do
  fn send(s : Socket, data : String) : Result((), Socket.SocketError) needs () do
    Socket.write(s, data)       -- fine: the socket was opened elsewhere, checked
  end
end

A handle is closed at its last use in compiled code. A handle is released when its last reference goes, which in a compiled program is right after the last line that mentions it; the interpreter keeps it until the program ends. That is usually what you want, with one trap: a Listener whose last use is Socket.local_port is closed before the next line, so a later connect to that port is refused, compiled only.

let l = ... Socket.listen(0) ...
let port = ... Socket.local_port(l) ...
Socket.connect("127.0.0.1", port)      -- refused: l was closed on the line above

Use the listener again where you are done with it (Socket.close_listener(l), or the accept loop that serves the port). The compiler warns (listener_closed_early) when a Socket.local_port(l) call is the last mention of l in its block and more of the block follows. The listener is not kept alive to the end of its scope instead: that would be an exception, for one type, to the last-use release that in-place updates rely on.

An operation is refused at run time when it lies outside the current authority: main’s request, narrowed by --grant or MARCH_GRANT at launch, and by each function needs clause and restrict block it runs under; see Run-time authority. UDP sockets and TLS contexts are handles opened by a checked open (Udp.open, Tls.client_ctx). HttpServer.listen, spawn_n and bind_host check IO.NetListen (on the port, a plain_listener port, the bind address) and return Result((), CapError) / Result(Int, CapError); Udp.resolve checks IO.NetConnect on its host:port and returns Result(Result(UdpAddr, UdpError), CapError). HttpClient and Tls.https_get still return their old types, but dial through Socket.connect, so their target is checked like any connect and a refusal is folded into their error.

Run-time authority: --grant, MARCH_GRANT and scoped function needs

The checks above prove, before the program runs, which capability kinds each piece of code may reach. Some things they cannot see: a path or host computed at run time, a launch narrowed by whoever starts the program, a function value called far from where it was made. So every running program also has a current authority, and each capability operation is checked against it. It works the same in the interpreter, --jit, the REPL, a compiled binary and --target js (the JS target has no tasks or actors); test/cap_conformance/ runs each of its fixtures in every one of the five that can run it (the JS target skips those that need tasks or actors). Not every rule below has a fixture yet.

The launch. A program starts with main’s request (see The grant): its needs clause and Cap(...) parameters, or the module’s needs line when it has neither. Whoever runs the program can narrow it, never widen it:

MARCH_GRANT='IO.Console, IO.FileRead("/srv/")' ./server
march --grant 'IO.Console' report.march         # interpreter, --jit
march repl --grant 'IO.Console' lib.march       # the REPL
forge run --grant 'IO.Console'                  # sets MARCH_GRANT for the run

The grant is a scope list in needs syntax; () grants nothing, and an empty MARCH_GRANT counts as unset. Each entry must lie within the request. A grant that does not parse, or that grants something main does not request, is a launch error: one line on stderr and exit status 2, before any of the program’s code runs, module-level lets included.

march: MARCH_GRANT is not a scope list: unexpected `;`
march: MARCH_GRANT grants IO.FileRead, which main does not request (main requests: IO.Console)

Scoped function needs. A function bound may carry scopes. While the function runs, its clause is a further limit around everything it reaches by direct calls, and the scopes are checked against the target each operation is actually given:

mod Conf do
  needs IO.Console
  needs IO.FileRead

  fn read_conf(name : String) : String needs IO.FileRead("/etc/myapp/") do
    match File.read("/etc/myapp/" ++ name) do
    Ok(Ok(text)) -> text
    Ok(Err(_)) -> ""
    Err(e) -> Authority.describe(e)
    end
  end
end

read_conf("../passwd") is refused: File.read returns Err, which Authority.describe renders as IO.FileRead("/etc/myapp/../passwd") refused by function read_conf's needs (IO.FileRead("/etc/myapp/")). Limits nest: inside a function called by another scoped function, under a narrowed launch, all three are in force (their intersection), checked from the innermost out, and a refusal names the innermost limit that refused (ByFnNeeds(f) with f’s clause, or ByLaunch with the grant text). A function already running under its own frame (its self-recursive calls) enters nothing again, so a self tail call stays a loop. When the function returns, the caller’s authority is back. A panic that unwinds out of a function and is caught (by a supervisor, a task join, a test runner) restores the authority in force where the catch was entered, so the unwound function’s clause is not left in force.

Path scopes compare whole segments lexically: a relative target is resolved against the current directory, . and .. are folded, and /srvx/y is not inside /srv/. Symlinks are not resolved (specs/todos/2026-11-17-ocap-path-scope-realpath.md). Host scopes compare the host (and port, and path prefix) a connection is opened to; name scopes the Vault or registry name.

Function values keep the authority they were made under. A lambda, or a named function used as a value, runs under the authority in force where it was created, however far it travels: one made inside a scoped function and called from main still runs under that function’s clause, and one made in main and handed to a scoped function runs under main’s authority, not the callee’s. The caller’s authority plays no part. A value made by module-level code (a top-level let’s initialiser) captures nothing and runs under its caller’s authority.

Actors and tasks keep their spawner’s authority for life. A worker spawned inside a scoped function stays limited by that function’s clause after the function returns. A supervisor that restarts a child restarts it under the authority of the child’s first spawn, whoever triggered the restart.

The REPL and tests. The REPL runs with the full authority of the person at the terminal; --grant narrows it. A test file runs under its module’s needs line, whatever main it declares; march test’s doctests run as the REPL does, with the full authority narrowed by a grant.

Cost. A program with no scopes, no grant and no scoped function pays two global loads per capability operation and one call at launch, and compiles to the same code otherwise. A check that walks the layers (under a grant, a scoped request, or inside a frame) costs well under a microsecond; entering a frame is a few tens of nanoseconds. Function values that reach a capability operation, a spawn or another function value carry one more word, but only in a program that has at least one frame.

Raw builtins are stdlib-only. A program cannot call a raw capability builtin (file_read(p), unix_time_ms(()), task_spawn(f)) directly: the reference is a stdlib_internal error that names the stdlib entry point to call instead (File.read, System.now_ms, Task.async, Crypto.random_bytes), which runs the run-time check first. Where the entry point takes the same arguments, the error carries the whole replacement call as its fix: file_read(p) becomes Authority.must(File.read(p)), which panics on a refusal.

Not yet enforced at run time. Authority does not travel with a remote child started on another node: the receiving node runs it under its own launch authority (specs/todos/2026-11-17-ocap-cross-node-authority.md). A module’s own scoped needs line is checked at compile time only, except as the program’s request when it is the entry module’s and main has none.

Narrowing a block: restrict

restrict SCOPE do ... end runs a block, and everything it reaches, under a narrower authority. Inside the block the authority is the intersection of the authority already in force and SCOPE; nested blocks intersect further, and nothing inside can widen it. Any code may restrict itself: writing restrict needs no needs line, and naming a kind the module does not hold is not an error, it simply adds nothing. restrict is an expression whose value is the block’s value, and restrict is a reserved word.

mod Report do
  needs IO.Console
  needs IO.FileRead

  fn load(name : String) : String do
    match File.read(name) do
    Ok(Ok(t)) -> t
    Ok(Err(_)) -> "missing"
    Err(e) -> Authority.describe(e)
    end
  end

  fn main() do
    let r = restrict IO.Console, IO.FileRead("/srv/data/") do
      load("/etc/passwd")
    end
    println(r)
  end
end

This prints IO.FileRead("/etc/passwd") refused by the restrict at report.march:14 (IO.Console, IO.FileRead("/srv/data/")). A refusal by a block is a value like any other, Err(CapError(kind, target, ByRestrict(where), scope_text)), where where is the source file’s base name and the line of the restrict keyword. Code loaded into the REPL names its file the same way; a snippet typed at the prompt is .:<line>. When the block ends, the authority in force before it is back, also when a panic unwinds out of it and is caught.

The scope list is one or more entries separated by commas, each a scope value or () (the empty scope: restrict () do ... end admits no capability operation at all). An entry may name any capability kind, the actor kinds included: inside restrict Actor.Introspect do ... end the block may mint the introspection capability (Actor.introspect()) and call Actor.pid_from_int, and nothing else, so a direct Actor.debug() there is cap_restrict at compile time.

The compile-time check. When every entry is written out (a literal scope expression such as IO.Console or IO.FileRead("/srv/"), or ()), the block is a literal restrict, and the compiler checks it like a function with a needs clause: every operation in the block, every direct call of a module-level function (with everything that function reaches), and every lambda or local fn made inside it must use only the kinds the scope names. A lambda or local fn made before the block and called inside it is a function value brought in, not a direct call: it is not charged to the block (see “What keeps the narrowed authority” below). A violation is the error cap_restrict:

`println` needs `IO.Console`, which the restrict at main.march:5 does not allow. [cap_restrict]
help: add `IO.Console` to the restrict, or move the call out of the block.

This check is by kind, as for needs: a path or host scope (/srv/data/ above) is checked at run time, against the target each operation is given. A call of a function value inside the block is not traced at compile time (the compiler cannot know which function it is); it is left to the run-time frame. When an entry is a value computed at run time (restrict s do), the block is a computed restrict and is checked at run time only.

When the run-time frame is kept. A literal restrict whose entries carry no scope (only kinds, such as restrict IO.Console do), and whose block reaches no actor spawn and no call of a function value, is fully proved by the compile-time check, so compiled code (native, --jit, the REPL’s JIT and --target js) emits no run-time frame for it and pays nothing to enter it. Every other restrict is a run-time frame: a literal one builds its layer once per program and then costs a few tens of nanoseconds per entry; a computed one parses its scope text at every entry (a few hundred nanoseconds). The interpreter always enters the frame. One consequence: Authority.check(...) inside a frame-dropped block, called directly or through a function the block calls, is not narrowed by the block in compiled code (the interpreter does narrow it). Every real capability operation in such a block has already been proved to lie within the block’s kinds, so nothing the block can do is affected.

What keeps the narrowed authority. Function values, tasks and actors created inside the block keep the block’s authority after it ends: a lambda made inside and called later from outside still runs narrowed, and an actor spawned inside is restricted for life, across supervisor restarts. Function values and pids brought in from outside keep their own: a lambda or local fn made before the block and called inside runs under the authority it was made under, not the block’s (a fn expression captures the authority where it is evaluated; see Run-time authority). A value made by module-level code captures nothing and runs under its caller’s authority, so inside a block it runs restricted. That includes a restrict written at module level (let reader = restrict IO.FileRead("/srv/") do fn p -> ... end): module-level code holds no authority of its own to park in the value, so the lambda it makes captures nothing, and it runs under whoever calls it, not narrowed by that block. There is no revocation: a value made inside a block cannot be widened again or cancelled later.

Not yet. A spawn budget (IO.Spawn(max(n))) is not part of the scope language, so a block cannot limit how many tasks it starts (specs/todos/2026-11-17-ocap-env-and-spawn-scopes.md). A literal target outside a scoped literal restrict (File.read("/etc/passwd") under restrict IO.FileRead("/srv/")) is reported when it runs, not at compile time (specs/todos/2026-11-17-ocap-scoped-fn-needs-literal-check.md). When a literal restrict is a function’s whole body, the function’s self call inside it is a tail call, so such a recursion runs as a loop. Otherwise a call in tail position inside a framed block is not a tail call: the stack grows by one frame per call through the block (the layer list does not), so a very deep recursion through a kept restrict, such as two functions whose restricts call each other, can overflow the stack.

Scope values: Scope and +

A scope is also a value of type Scope. In expression position, a constructor written with a capability path is a scope expression, and its arguments follow the needs grammar (strings first, then the literal options methods(...), prefix("..."), no_redirects):

let a = IO.Console                                   -- Scope
let b = IO.FileRead("/srv/") + IO.NetConnect("api.example.com", methods(get))  -- Scope
let c = IO.FileRead(dir)                             -- Result(Scope, ScopeError)
  • Literal. When every argument is a literal, the expression has type Scope and is checked at compile time with the same validator as a needs line (an invalid one is invalid_cap_scope). Literals follow the needs grammar, which folds . and .. segments lexically, so IO.FileRead("/srv/../etc/") is accepted and means /etc/.
  • Computed. When any string argument is an expression, the type is Result(Scope, ScopeError) and the arguments are checked when the value is built: a .. path segment or a malformed host is Err(ScopeError(message)), such as IO.FileRead: the path "/srv/../etc/" has a .. segment. Bind it with let?; passing the Result itself to restrict is a type error whose hint says so. Option arguments (methods(...) and the rest) must still be literal.
  • + is the union. a + b is a Scope with the entries of both; () adds nothing. A + chain of literal entries is itself literal (restrict IO.Console + IO.FileRead("/srv/") do is a literal restrict), while a restrict over a variable is computed, whatever the variable holds.
  • A scope grants nothing. Its only use is as restrict’s argument. It shows as its source text (to_string(IO.Console + IO.FileRead("/srv/")) is IO.Console, IO.FileRead("/srv/")) and has no Eq, because two lists with the same entries in a different order are the same scope.
fn under(dir : String) : Result(String, ScopeError) do
  let? s = IO.FileRead(dir)
  Ok(restrict s, IO.Console do load("/etc/hosts") end)
end

under("/srv/") is Ok of a refusal naming the restrict at that line; under("/srv/../etc/") is the ScopeError above, before the block runs.

Dependency grants: grant in forge.toml

A project can limit what each of its dependencies may do. A grant on a dependency in forge.toml is a scope list in needs syntax, written as a list of strings:

[deps]
weather = { path = "../weather", grant = ['IO.NetConnect("api.weather.test/v1/", methods(get))'] }
shout   = { path = "../shout", grant = ["IO.Console"] }
pure    = { path = "../pure", grant = [] }     # grants nothing
legacy  = { path = "../legacy" }               # no grant: as before

[deps.reader]
path  = "deps/reader"
grant = ['IO.FileRead("/srv/data")']

Single-quoted strings are TOML literal strings (no escapes), which saves escaping the quotes inside a scope. grant is accepted on [deps], [dev-deps], [dev-only-deps] and [test-deps] entries, inline or as a [deps.X] section. Every entry is checked like a needs line; a malformed one is the error dep_grant_invalid, reported at its forge.toml line.

What it means. A grant is a limit around every function defined in the dependency’s package. While any of them runs, the authority is the caller’s authority intersected with the grant (and with the function’s own needs, as always). A grant never widens anything: it cannot give a dependency a capability its caller lacks, and it adds nothing the dependency’s own needs lines do not already declare. grant = [] grants nothing, so the dependency may still compute but no capability operation it reaches is allowed.

A dependency with no grant keeps the behaviour it has always had: it is limited only by its own needs and by its caller’s authority. It gets no frame and costs nothing. forge audit marks it no grant, so an unlimited dependency is visible in review.

Only reached code counts. The compiler checks, by kind, everything the program reaches in a granted package: every package function called from outside it (directly, as a value, or through an interface method on one of the package’s types), everything those reach, and the package’s module-level code. A function the program never reaches may need anything, except C code (see extern below). A reached violation is a build error that names the dependency, the forge.toml line, the capability and the call chain:

`cpid` is granted `IO.Console`, but `Cpid.getpid` needs `IO.Foreign` (`Main.main → Cpid.pid → Cpid.getpid`). [dep_grant_exceeded]

7 |     println(int_to_string(Cpid.pid()))
                              ^^^^^^^^

    granted at forge.toml:2
    hint: widen the grant in forge.toml, or stop calling `Cpid.pid`

Under a scoped grant, a literal target outside the scope is also caught at compile time, as dep_grant_scope (a literal URL or a literal-prefix ++ at a network entry point, a literal path, a literal Vault or registry name):

`weather` is granted `IO.NetConnect("api.weather.test/v1/", methods(get))`, but `Weather.Telemetry.ping` connects to `https://telemetry.example.net/ping` (`Main.main → Weather.forecast → Weather.Telemetry.ping`). [dep_grant_scope]

A target computed at run time is checked when it runs. A refusal is a value like any other, Err(CapError(kind, target, ByGrant("<package>"), "<grant text>")), which Authority.describe renders as IO.FileRead("/etc/hosts") refused by the grant to package reader (IO.FileRead("/srv/data")).

What the reach cannot see. The compiler follows an interface method called from outside the package into the package’s impl only when it knows the type of the call’s first argument. A call left generic (a function of yours that takes x and calls peek(x), a method passed as a value, generic stdlib code calling compare or hash on the package’s type) counts no impl, so ordinary generic code can reach package code the build did not check (specs/todos/2026-11-23-grant-dispatch-type-first-arg-only.md). That code still runs under the grant: the run-time frame refuses whatever capability operation it attempts beyond the grant, for every capability, IO.Foreign included (below).

extern. C called from a granted package counts as IO.Foreign, and unlike the other kinds it is checked package-wide: when any function of a granted package can reach an extern (one it declares, another package’s, or a stdlib module built on one), the grant must name IO.Foreign, whether or not the program calls that function:

`cpid` is granted `IO.Console`, but `Cpid.getpid` needs `IO.Foreign` (`peek in impl Peek(Tok) → Cpid.getpid`), and a granted package reaches C code only under a grant that names it. [dep_grant_exceeded]

C reached at run time while a grant that does not admit IO.Foreign is in force (an ungranted package’s impl, say, that a granted package reaches through generic code) is refused before it runs, on every backend: the program panics with capability refused: IO.Foreign refused by the grant to package pidshow (IO.Console), which __try_call_val can catch. An extern returns a plain value, so this refusal cannot be an Err. Only a grant refuses C this way: code outside every grant frame, including a callback the app hands a granted package, calls its externs as before.

Interface default bodies. A default method body is the code of the package that declares the interface. An impl that inherits it runs it under that package’s grant, wherever the impl is written, and the compiler charges it to that package: an app’s empty impl Greet(Mine) of a granted package’s Greet whose default prints is a dep_grant_exceeded under a grant without IO.Console. A method the impl writes itself is the impl’s own package’s code. The methods of a derived impl written in a granted package get no grant frame yet; they are pure today (specs/todos/2026-11-22-grant-untagged-package-code.md).

Transitive dependencies. A package that a granted dependency calls directly runs under that dependency’s grant while it is called from there, whether or not it has a grant of its own. If the project grants it too, both limits hold, and a refusal names the innermost one that refused. Called directly from the app, it is limited only by its own grant (if any). Only the root project’s forge.toml grants: a grant written in a dependency’s own manifest is not applied, and forge audit lists it as not applied (specs/todos/2026-11-22-ocap-nested-manifest-grants.md).

Callbacks and returned values. A function value the app passes into a granted dependency was made by the app, so it runs with the app’s authority, as any function value keeps the authority it was made under (run-time authority). A closure, task, actor or handle the dependency makes and hands back carries the dependency’s narrowed authority, wherever it ends up. An actor declared in a granted package runs its handlers under its spawner’s authority intersected with the grant.

Module-level code. A granted package’s module-level lets run under the launch authority narrowed by their module’s needs and by the grant. A function value made there (a lambda, or a package function named as a value) captures nothing and behaves as one of the package’s named functions: it runs under its caller’s authority intersected with the grant. So a package cannot park let leak = fn url -> HttpClient.get(url) at top level and call out of its grant through it.

Packages. A module belongs to the package whose library root contains its source file’s real path (the longest such root, so nested roots work). A file that lies under a granted root but is a symlink to code outside it is dep_grant_invalid. While any grant is in effect, two modules with the same name in different places are an error, dep_module_conflict: the app and a dependency, two dependencies, or a dependency and the standard library (“Module Csv is defined twice under dependency grants”), and so is a granted library root inside the entry’s source directory or inside another library directory, since its modules would also load as the app’s. A build with no grants keeps the old first-one-wins behaviour.

forge and the grants file. forge passes the grants to the compiler as a file, named by MARCH_DEP_GRANTS. It writes the file as .forge/dep-grants-<md5 of its text> only when a dependency in the command’s scope has a grant; otherwise it writes nothing and leaves the variable unset. A granted dependency that is not installed, or whose library root is not on the library path, is an error. forge clean removes old grants files. The grants file’s digest is part of every compile, check and interpreter cache key, so editing a grant rebuilds what it affects.

Without forge, pass the file yourself with --dep-grants FILE (or MARCH_DEP_GRANTS=FILE; the flag wins). It works for march FILE, --check, --compile, --jit, march repl, march test and march dap. The format is UTF-8 text, one package per line, four tab-separated fields; a line starting with # is a comment:

<package>	<library root, absolute>	<manifest>:<line>	<scope text>
reader	/home/me/app/deps/reader/lib	/home/me/app/forge.toml:11	IO.FileRead("/srv/data")
pure	/home/me/pure/lib	/home/me/app/forge.toml:12	()

The scope text is the grant’s strings joined with ", ", and () means grant = []. The library root must be one of the MARCH_LIB_PATH directories or a parent of some of them. A relative root, a root that does not exist or is off the library path, a field with a tab in it, a duplicate package or a malformed scope is dep_grant_invalid, at the manifest line. march repl FILE runs the same grant checks on its entry file and refuses to load a file that breaks them, or when the check does not finish (it crashed or was killed); a file with ordinary errors still loads, and the REPL reports them. A file :loaded later in the session is not checked statically, but the run-time frames still refuse what its grants do not allow.

When the frame is kept. Calls from inside a package to its own functions go straight to their bodies, so only a call that crosses into the package pays for the frame, about 16 ns per call (bench/grant_enter.march). Entering a grant that is already in force pushes nothing, so recursion in and out of a package does not grow the layer list. In compiled code (native, --jit, the REPL’s JIT and --target js) a package function enters no frame at all when the grant carries no scope (only kinds, such as grant = ["IO.Console"]), the compiler proved everything the function reaches lies within the grant’s kinds, and the function reaches no actor spawn, no call of a function value and no interface method left generic (such as the show(x) inside the polymorphic println). A package function that calls Authority.check itself is never proved this way. The interpreter always enters the frame. A call into a granted package’s kept frame is not a tail call, so a very deep recursion that crosses into a granted package on every step can overflow the stack (specs/todos/2026-11-26-grant-frame-tail-calls.md). Tail calls between functions with scoped needs clauses are tail calls: when the callee’s frame is already in force the call goes straight to its body.

Auditing grants. forge audit prints each dependency’s grant beside its capabilities (reader — IO.FileRead — grant: IO.FileRead("/srv/data"), or — no grant), and forge audit --record writes it into forge.caps.lock. A grant that was widened or removed since the recorded baseline is an escalation and fails the audit, like a dependency that asks for more; a grant narrowed or newly added is reported but does not. See Capability audit.

When not to use IO caps

Pure functions need no declaration. If a function hashes a string, parses JSON, sorts a list, or formats a number, write no needs. A module with no needs that calls IO builtins directly in function bodies is rejected (--check exits 1); a stdlib-mediated call is outside that check but is caught by the upper limit, which runs in every mode. The one exception is IO.Foreign, which the upper limit excludes: a module with no needs can call a first-party stdlib module built on extern (Js.Dom, Js.Canvas on --target js), and only a function-level needs () bound or main’s grant reports that reach. The guarantee is strongest when the functions in question actually take Cap(X) parameters or use something that does, because the compiler cannot force you to declare a capability that never appears in a signature and is never transitively required by an import.

Don’t over-narrow to look principled. Declaring needs IO.FileRead when your function also writes is a lie the compiler will catch. If a function reads and writes, needs IO.FileSystem is correct even if it feels less precise. Accurate beats narrow-but-wrong.

Don’t use IO caps for pure domain concepts. A function that validates an email address or checks a constraint has no business with capabilities. Capabilities exist for external state, not for logic.

Don’t use capabilities for per-value guarantees. needs IO.FileRead says a module is allowed to read files; it says nothing about whether a specific string value came from a trusted source. For per-value guarantees, use an opaque refined type.

Small scripts: just use needs IO. For a 50-line script you will run once, fine-grained capability declarations add more friction than value. Use needs IO at the top and move on. The value of narrow caps emerges in larger codebases with multiple contributors over time.

Specific IO capabilities

IO.Mut: shared mutable state

IO.Mut covers Vault tables: process-global shared mutable hash maps. A module with no needs IO.Mut is statically proven never to touch shared mutable state:

mod Cache do
  needs IO.Mut

  fn store(key : String, val : Int) : () do
    let tbl = Vault.new("app_cache")
    Vault.set(tbl, key, val)
  end
end

This is especially useful for library code that should have no hidden state.

Reads need no capability. A Vault table is in-memory: no part of what a Vault.get/Vault.size/Vault.keys lookup does escapes the process, so it exercises no ambient authority and needs no needs IO.Mut. What IS authority is turning a NAME into a table handle (Vault.new/Vault.whereis, the File.open(path) shape) and mutating state other actors observe (Vault.set, Vault.set_ttl, Vault.drop, Vault.update); those keep needs IO.Mut. Accepted trade-off: a read of shared mutable state is non-deterministic (it observes another actor’s writes), so needs no longer signals “this function is not pure” for a reader. Authority stays auditable at the boundary, since some module still had to name the table and declare the capability to create or write it.

IO.Registry: naming and finding actors

IO.Registry covers the named actor registry: Actor.register, Actor.unregister, Actor.whereis and Actor.registered. Finding an actor by name turns a string into a Pid, which is a capability, and registering a name can impersonate the actor others expect behind it, so both are authority. A module that calls them declares needs IO.Registry (or needs IO); the missing-capability error carries the line as a machine fix, so forge fix adds it. Actor.whereis and Actor.registered still take a Cap(Actor.Introspect) as well.

mod Pool do
  needs IO.Registry

  fn publish(pid) : Bool do
    Actor.register(pid, "pool")
  end
end

IO.Cluster, Actor.Introspect and Actor.Debug: the checked witness operations

These kinds gate the operations that once took the root Cap(IO) as a witness argument (ocap phase 7). Each is a checked operation that returns Result(_, CapError) and is charged to the code that calls it, so main must request the kind:

Operation Kind Returns
Actor.introspect() Actor.Introspect Result(Cap(Actor.Introspect), CapError)
Actor.pid_from_int(n) Actor.Introspect Result(Pid(a), CapError)
Actor.debug() Actor.Debug Result(Cap(Actor.Debug), CapError)
Session.attach(ops) IO.Cluster Result(Cap(Session.Live), CapError)
ClusterNode.attach(ops) IO.Cluster Result(Cap(ClusterNode.Live), CapError)
ClusterNode.start(cfg) IO.Cluster Result(Cap(ClusterNode.Live), String) (a refusal is its Authority.describe)

The capabilities they return are unchanged: holding a Cap(Actor.Introspect) is still the right to call Actor.whereis, Actor.list, the Recon functions and the rest without a further check.

mod Observer do
  needs IO.Console

  fn main() : () needs IO.Console, Actor.Introspect do
    let c = Authority.must(Actor.introspect())
    println(int_to_string(List.length(Actor.list(c))))
  end
end

Name scopes on IO.Mut and IO.Registry

IO.Mut and IO.Registry take a scope of names, and of name prefixes written prefix("..."):

mod Sessions do
  needs IO.Mut("sessions")                         -- only the "sessions" table
  needs IO.Registry("logger", prefix("worker."))   -- "logger" and any "worker.…"

  fn start(pid) : Bool do
    Actor.register(pid, "worker.1")                -- in scope
  end
end

A name is in scope when it equals one of the names or starts with one of the prefixes: prefix("worker.") admits "worker.1" but not "worker" or "workers.1". A name or prefix may not be empty or contain ;, = or ,; anything else is invalid_cap_scope.

What is checked, at compile time. In a module whose own needs scopes the capability (and grants no unscoped IO.Mut, IO.Registry or IO), each call of Vault.new, Vault.open, Vault.whereis, Vault.ns_set, Vault.ns_get, Vault.ns_drop, Config.new_store, Actor.register, Actor.unregister and Actor.whereis, in any of the module’s code (functions, actors, impl methods, tests and setup blocks) and through an alias of Actor or Vault:

  • with a literal name outside the scope is a cap_scope_violation naming the scope;
  • with a computed name ("worker." ++ id) is refused too: the compiler cannot prove it is within the scope (a name scope on main’s request or on a function needs clause is checked at run time instead, see Run-time authority);
  • a name-taking function used as a value (let f = Actor.register) is refused for the same reason.

Actor.registered lists every name, which exceeds any name scope, so it needs an unscoped IO.Registry. A nested module may narrow its parent’s name scope but never widen it: under a parent’s needs IO.Registry("logger"), a nested needs IO.Registry (or needs IO) is a cap_scope_violation. Not yet checked: a name passed through a function written in another module (Reg.put(pid, "other")). The run-time check closes it only under a scoped request or function clause, not for a module’s own needs line (specs/todos/2026-11-13-name-scope-bypasses.md). A lookup by name is an open: Vault.whereis("tokens") under needs IO.Mut("sessions") is refused.

IO.NetConnect.TLS: encrypted transport only

IO.NetConnect.TLS is a child of IO.NetConnect. Declaring it (without IO.NetConnect) proves the module uses only encrypted connections, no plaintext TCP. Declaring needs IO.NetConnect covers both.

mod HttpsClient do
  needs IO.NetConnect.TLS  -- plaintext TCP is statically excluded

  fn context() do
    Tls.client_ctx(Tls.default_client_config())
  end
end

IO.Telemetry: observability annotation

IO.Telemetry is declaration-only: the compiler accepts it as a semantic annotation but does not scan for specific builtins. Use it to make telemetry visible in a module’s surface contract so callers know this module emits observability data:

mod Metrics do
  needs IO.Telemetry

  fn record_request(duration : Int) : () do
    ...
  end
end

IO.Foreign: calling unverified C

IO.Foreign is a meta-capability triggered by the presence of an extern block, not by any specific builtin call. C code bypasses every March type guarantee, so the compiler requires you to acknowledge this explicitly.

mod Bindings do
  needs IO.Foreign
  needs IO.FileSystem  -- the specific cap the C code uses

  extern "libc": Cap(IO.FileSystem) do
    fn read(fd : Int, buf : String, n : Int) : Int
  end
end

The blocking modifier spawns an OS thread. Declare both caps when any extern function is blocking:

mod Bindings do
  needs IO.Foreign
  needs IO.Foreign.Blocking
  needs IO.FileSystem

  extern "libc": Cap(IO.FileSystem) do
    blocking fn slow_read(fd : Int) : Int
  end
end

needs IO.Foreign on its own subsumes IO.Foreign.Blocking (parent covers child), so one declaration satisfies both requirements if you prefer coarser annotations.

Behavioral module caps: cap no_panic, cap no_alloc, cap no_extern, cap pure, cap deterministic

Beyond IO permission caps and proof caps, March has five behavioral capability declarations that trigger static analysis passes rather than IO-permission accounting. They share only the cap keyword with needs/Cap(X): a module can declare cap no_panic and separately declare needs IO.Network, and the two mechanisms never interact. Each lives as a bare cap <name> statement in the module body.

cap no_panic: guaranteed panic-free

mod SafeMath do
  cap no_panic

  fn divide(a : {v : Int | v >= 0}, d : {v : Int | v > 0}) : Int do
    a / d
  end
end

A module with cap no_panic must not contain any expression that can panic at runtime. Four checks enforce that, covering four different ways code panics: an unsafe call, an unsafe division, an unhandled match case, and Int arithmetic that overflows.

1. Unsafe calls. Some functions can panic: panic itself, List.tail on an empty list, Option.unwrap on None. The compiler splits these into two groups:

  • Always banned, no way around it: panic/panic_/todo_/unreachable_. No code you write can make these safe, so cap no_panic simply forbids calling them, directly or through a local helper that calls them (a helper that panics makes every one of its own callers unsafe too, and each gets its own error).

  • Allowed if you prove it’s safe: partial functions that come with a refinement precondition: List.nth, List.tail, List.head, Option.unwrap, Result.unwrap, Random.choice_weighted, Stats.percentile, Array.get/Array.set/Array.pop (index in bounds; pop on a non-empty array), and similar. Guard the call with something that proves the precondition, and it is accepted:

    mod Safe do
  cap no_panic
  -- Accepted: the guard proves `len(xs) > 0`, which is List.tail's contract.
  fn rest(xs : List(Int)) : List(Int) do
    if List.length(xs) > 0 do List.tail(xs) else xs end
  end
  -- Accepted: the guard proves the index is in bounds, Array.get's contract.
  -- Without it (or with `i <= Array.length(v)`) this is a panic error.
  fn at(v, i : Int) : Int do
    if i >= 0 && i < Array.length(v) do Array.get(v, i) else 0 end
  end
end

    This reuses the same proof the refinement checker already produces: it does not derive anything a second time, so the two cannot drift apart. Only a full proof counts: an unproven guard, a skipped check, or an @[trusted] assertion all still produce the panic error. (@[trusted] in particular is intentional: a capability whose whole point is “guaranteed no panics” cannot accept, with no visible sign, an unchecked assertion as if it were a proof.)

    Not every panic on a guarded function is covered. The precondition only expresses what the type system can see: usually “the list isn’t empty.” Random.choice_weighted also panics if every weight is zero or any weight is negative, but that depends on the actual Float values in the list, not its length, so no refinement can rule it out. A cap no_panic module that calls it with a proven-non-empty, all-zero-weight list compiles clean and still panics at runtime. Stats.correlation and Stats.linear_regression have the same gap: their length preconditions are checked, but a zero-variance input still panics. If you rely on cap no_panic for one of these functions, know which panic you are actually protected from.

2. Unsafe division. Every integer division needs its divisor proven non-zero: via the Z3 SMT solver for anything non-obvious, with fast syntactic shortcuts for common patterns (v > 0, v != 0, and so on) so the obvious cases do not need a solver at all. An enclosing if guard, or a match arm’s when guard, counts as proof on the branch it protects: if d != 0 do n / d else 0 end needs no refinement, and neither does the safe side of if d == 0 do 0 else n / d end. Guards combined with &&/||/not are read correctly: an && guard is proven by either side, an || guard only when both sides independently rule out zero. Anything left over (no refinement, no guard, an expression the checker does not recognize) is a conservative error. If Z3 itself is unavailable, the check stays conservative rather than skipping: an unverified division is still treated as an error, not silently allowed.

Use Math.checked_div / Math.checked_mod when you cannot prove the divisor is non-zero statically: they return Option(Int) instead of panicking.

3. Non-exhaustive match. In an ordinary module, a match that does not cover every constructor is a warning: the build still succeeds. Under cap no_panic it is an error: an uncovered case is a runtime panic waiting to happen (“no matching clause”), and excluding that is exactly what the capability promises.

4. Int overflow. +, -, * and unary - on Int panic when the result leaves [-2^62, 2^62) (see Int width and overflow). Under cap no_panic each one must be proven to stay in range, by the same machinery as division: refinements on parameters, enclosing guards, and let values in scope. The checker knows that every Int a program holds is already in range (a value outside it would have panicked where it was computed), so x - 1 under x >= 0, x + 1 under x < n, and x * x with x refined to {v : Int | v >= 0 && v < 1000} are all accepted, while a bare x + 1 on an unrefined x is an error that names a value it cannot rule out (x = 4611686018427387903). Float arithmetic never traps and is not checked. When wrapping is genuinely what you want, or a counter is bounded by something the checker cannot see (a byte offset into the input, say), spell it int_wrapping_add / int_wrapping_sub / int_wrapping_mul: those wrap modulo 2^63 and never panic. int_abs, int_pow and int_shl also still wrap and are not checked.

One tooling caveat: march check (the fast, package-level command) does not run the same proof infrastructure as march --compile/--check, so for the “allowed if you prove it” functions above it falls back to banning them by name rather than checking your guard. That means march check can reject a call that march --compile accepts. It is being more conservative, not wrong. The LSP has the same limitation inside a top-level module (nested modules get full proof-based squiggles).

cap no_alloc: no heap allocation

mod RealTimeDSP do
  cap no_alloc

  fn mix(a : Float, b : Float, gain : Float) : Float do
    (a + b) * gain
  end
end

cap no_alloc puts every function in the module (nested modules, impl methods and actor handlers included) under a hard @[no_alloc] contract (see surface syntax). There is one check, and the cap and the attribute get the same answer from it. It runs on the compiled program, after Perceus reference counting and escape analysis, so:

  • a constructor the compiler reuses in place (a functional-but-in-place update of a value nothing else holds) passes, and so does a value it promotes to the stack;
  • it is transitive: a call into a helper that allocates fails, and the error names the helper and what it allocates;
  • the error names the cap: `mix` is in `cap no_alloc` module `RealTimeDSP` but allocates.

What fails is whatever the compiled code actually allocates: a tuple, record or closure that is built rather than reused, a record update, string concatenation and interpolation, a Float boxed where it crosses an erased slot, a call through a closure or an extern the checker cannot see into. Nullary constructors are not automatically free: an all-nullary enum and a niche-shaped Option compile to immediate tags, but a nullary case of a type that also has payload-carrying cases (Nil of List) is a real 16-byte heap cell, so a function that returns a fresh Nil fails while one that returns the empty list it matched passes.

An explicit per-function form inside the module wins, so one helper can opt out visibly: @[no_alloc(warn)] turns its failure into a warning, @[no_alloc(assume)] asserts it (for a call the checker cannot see through), and @[no_alloc(transient)] allows allocations released before it returns.

Where it is judged: march --compile, forge build/forge test, the editor, march --check and march check (which lower the program on demand when, and only when, it contains a cap no_alloc module or an @[no_alloc] function; a program that cannot be lowered gets a no_alloc_unchecked warning per function instead of a verdict). The interpreter, --jit, the REPL and march test never lower, so they cannot judge it: they print one no_alloc_unchecked hint and run the program. --no-opt downgrades a hard failure to a warning, since the reuse the verdict relies on comes from the optimiser.

cap no_extern: no foreign calls

mod NoFFIService do
  cap no_extern
  needs IO.Network

  fn ping(host : String) : Int do
    string_length(host)
  end
end

A module with cap no_extern may not contain an extern block and may not declare needs IO.Foreign: either one is an immediate error. Useful for a module that must stay pure C-free code, e.g. because it needs to run somewhere extern’s FFI trust boundary is not available.

cap pure: no side effects at all

mod PureMath do
  cap pure

  fn add(a : Int, b : Int) : Int do
    a + b
  end
end

A module with cap pure bans every call to a builtin that performs any side effect (file IO, network IO, spawning, sending, vault access, console output, randomness, the clock), as well as spawn/send/exit and the monotonic clock read sys_uptime_ms. The banned set is derived from the same authoritative builtin-to-capability table (builtin_cap_table) the ordinary IO-cap body-scan check consults, so it stays in sync with the real builtin surface: a module declaring cap pure and calling file_write is rejected:

$ march --check leaky_pure.march   # cap pure; fn write(...) : Result(Unit, String) do file_write(path, contents) end
-- CONTRACT -- `write` in `mod LeakyPure` (declared `cap pure`) calls `file_write`, which has side effects.
$ echo $?
1

The check covers stdlib wrappers too, by two rules. A cap pure module may not declare any needs: a pure module holding a capability is a contradiction, and every stdlib wrapper over a capability-gated builtin (File.read, DateTime.now, …) is reachable only from a module that declares its needs, so rejecting the needs line closes that route. A banned builtin that needs no capability (the monotonic clock behind System.monotonic_time, spawn, send, exit) is followed through the stdlib: a call to a stdlib function that reaches one is rejected like a direct call.

$ march --check pure_clock.march   # cap pure; fn t() : Int do System.monotonic_time() end
-- CONTRACT -- `t` in `mod Pure` (declared `cap pure`) calls `System.monotonic_time`, which has side effects: it reaches `sys_uptime_ms`.
$ march --check pure_needs.march   # cap pure; needs IO.FileRead
-- CONTRACT -- `mod Pure` (declared `cap pure`) declares `needs IO.FileRead`, but a pure module cannot hold a capability: …

Calls through user-defined modules are outside both caps: each module is checked against its own declarations.

cap deterministic: no clock, no randomness

mod DeterministicSim do
  cap deterministic

  fn checksum(bytes : String) : Int do
    string_length(bytes)
  end
end

cap deterministic is strictly weaker than cap pure: it bans only the two nondeterminism sources (wall-clock/monotonic-clock reads and random-number generation), so a cap deterministic module may still perform ordinary IO such as file_read, as long as it never touches the clock or an RNG. The same two rules carry it through stdlib wrappers: the module may not declare needs IO.Clock, needs IO.Random or needs IO (which includes both), so DateTime.now and the RNG wrappers are out of reach, and a stdlib call that reaches the ambient monotonic clock (System.monotonic_time) is rejected like a direct sys_uptime_ms():

$ march --check clock_leak.march   # cap deterministic; calls unix_time_ms(())
-- CONTRACT -- `now` in `mod DetLeak` (declared `cap deterministic`) calls `unix_time_ms`, which is non-deterministic.
$ echo $?
1

History: both cap pure’s and cap deterministic’s banned-builtin sets used to be hand-maintained name lists that referenced builtins spelled wrong or that never existed (write_file, random_int, now_ms) while missing the real ones (file_write, random_bytes, unix_time_ms), so the two caps silently failed to catch the most common effectful calls. Both sets are now derived from the compiler’s single authoritative effect map. The fix changed which calls each cap catches, not what either cap means.

Choosing among the five

I want to… Use
Prove no integer division or arithmetic can panic, and rule out non-exhaustive matches cap no_panic + Int refinements on divisors and operands
Guarantee safe use in a realtime audio callback cap no_alloc, checked on the compiled code by forge build, march --check and the editor (+ Tagged(DSP, Realtime) for the calling site)
Keep a module free of C/FFI trust-boundary crossings cap no_extern
Guarantee a module has zero side effects, not just no IO caps declared cap pure
Guarantee reproducible output (no clock, no RNG) while still allowing ordinary IO cap deterministic
Both: pure, panic-free, zero-alloc cap no_panic and cap no_alloc together

All five declarations can coexist in the same module. Each is checked by its own independent pass, and none of them subsumes or implies any other. (cap no_alloc is judged on the compiled program rather than during typechecking, so the interpreter reports it as unchecked; see above.)

Capture sets: what a function value can reach

Since object capabilities, a function value runs under the authority it captured where it was made, not its caller’s (see “Function values keep the authority they were made under” above). So passing a closure around passes authority around, and the plain type String -> () does not say how much. The compiler now infers that for every function value and for every value that holds one. It is called the value’s capture set: an upper bound on what the value can do when it is called.

The sets are inferred. Nothing is written in source yet and nothing is rejected because of them: this is the first step of capture checking (design: specs/2026-11-11-ocap-capture-checking-design.md). You can read them in two places.

In the editor. Hover shows a value’s type with its set after needs:

let say = fn s -> println(s)       -- say : a -> Result((), CapError) needs IO.Console
let weather = Weather.new()        -- weather : Client needs IO.NetConnect("api.weather.com/v1/")

march-lsp query type and query hover print the same text. A value that holds no function value prints exactly as before.

From the command line. march --dump-captures FILE checks the file and lists every place a function value is made, with its set and the reason for each element:

8:11   lambda in `new`  needs IO.NetConnect("api.weather.com/v1/")
         IO.NetConnect("api.weather.com/v1/")  calls `HttpClient.get` (9:12)
17:13  let fetch : String -> Result(String, String) needs c1
26:8   let weather : Weather.Client needs IO.NetConnect("api.weather.com/v1/")
fn new : () -> (Weather.Client needs IO.NetConnect("api.weather.com/v1/"))
fn print : (Weather.Client needs c1) -> Result((), CapError) needs IO.Console, c1
1 function value, 0 not tracked

How to read it:

  • A scope such as IO.Console or IO.FileRead("/srv/data/") means the value can perform operations inside that scope. A literal target gives a scoped element; a computed one gives the whole kind.
  • A variable such as c1 stands for whatever a parameter carries. print above calls a function it was handed inside the Client, so calling print may do whatever that client can: needs IO.Console, c1.
  • Data holds what its fields hold. A Client built around a closure has that closure’s set: Client needs IO.NetConnect(...). A type argument carries its own set: List((String -> () needs IO.Console)).
  • A set is what the value can do, not what it may try. A closure created inside a literal restrict is narrowed by it, as is one created in a function with a needs clause. A value that a call returns, or that was made outside and brought in, keeps the set it had: it runs under its own authority.
  • not tracked (printed ?, and IO in a hover) marks a value the inference does not follow, for example a function value read from a table opened by name. It is treated as able to do anything. It is never a smaller set than the truth.

A function value made by module-level code captures nothing at run time and runs under its caller’s authority, so its set is everything it can reach and a module-level restrict does not narrow it.

Capability inference hints

If you call a function that requires a needs X declaration but your module does not have one, the compiler emits a hint (not an error) pointing to the call site:

hint: this call uses IO.FileRead but mod Config does not declare `needs IO.FileRead`.
hint: add `needs IO.FileRead` to the module body.

This is informational, and it is not necessarily backed by a type error. The hint pass (cap_infer.ml) runs after typechecking and shares the same underlying builtin-capability table as the typechecker’s own body-scan check. That body-scan check is itself an ERROR for an undeclared direct builtin call (see What the compiler tells you), so a module that declares no covering needs at all is rejected regardless of the hint. But a hint can still appear on a program that --checks clean (exit 0); in that case the hint is the whole story, not a preview of a rejection.

Putting it together

Here is how capability declarations compose across a small web application. Reading the needs list of each module answers “what does this module do to the world?” without opening the implementation:

mod AppConfig do
  -- Note: named `AppConfig`, not `Config` — `Config` is already a stdlib
  -- module (`stdlib/config.march`), and a user module of the same name
  -- would collide with it once this file joins a real multi-file build.
  needs IO.FileRead          -- reads one config file, nothing else

  type AppConfig = AppConfig

  fn load(path : String) : AppConfig do ... end
end

mod Metrics do
  needs IO.Telemetry         -- makes observability a visible architectural concern

  fn record(event : String, duration : Int) : () do ... end
end

mod Api do
  -- Likewise `WebServer`/`ConnCtx` here, not `HttpServer`/`Conn` — those
  -- names are already taken by stdlib's `HttpServer` module.
  use WebServer

  needs IO.NetListen         -- binds a port
  needs IO.NetConnect.TLS    -- outbound HTTPS only — no plaintext TCP
  needs IO.Mut               -- session vault

  fn start() : () do
    WebServer.new()
    |> WebServer.plug(fn conn -> handle(conn))
    |> WebServer.run(8080)
  end
end

mod Main do
  use AppConfig
  use Api

  needs IO

  -- The program's request: what `main` and everything it reaches may use.
  fn main() : () needs IO.FileRead, IO.NetListen, IO.NetConnect.TLS, IO.Mut do
    let config = AppConfig.load("/etc/myapp/config.toml")
    Api.start()
  end
end

AppConfig is verifiably read-only. Api cannot read files and cannot use plaintext TCP. If AppConfig.load at any point called a network function, the build would fail until needs IO.NetConnect was added: no audit needed.

Runtime behaviour

A capability value (a proof capability, Cap(X)) is a nullable pointer. By default it is null, compiling to null in LLVM IR and VUnit in the interpreter, with no allocation, no indirection and no overhead; that is what every capability is unless something explicitly attaches a runtime dictionary to it. Enforcement of the capability types is at compile time; what a run may do is also checked at each capability operation against the run-time authority, at the cost of two global loads when no grant, scope or frame is in play. A compiled binary can additionally turn its declared set into a kernel-enforced sandbox at startup, and a running node can gate hot deploys against it. Both live on their own page: see Capability Enforcement (OS-level sandboxing via forge cap run / --cap-sandbox, and node-local hot-deploy admission control).

Proof caps: encoding initialization order

IO caps control which resources a module may touch. Proof caps control when dependent code may run. They are separate concerns.

The problem they solve

Some operations must happen before others:

-- What stops someone calling this before run_migrations?
fn query(sql : String) : List(Row) do ... end

A proof cap makes “migrations have run” part of the type:

mod Db do
  proof cap Migrated
  needs IO

  fn run_migrations() : Cap(Db.Migrated) do
    -- do the real migration work, then mint the proof.
    -- `mint_cap()` is the sanctioned way to construct a proof cap; it typechecks
    -- ONLY here — inside a public `fn` of the declaring module. Runtime-erased.
    mint_cap()
  end

  fn query(m : Cap(Db.Migrated), sql : String) : List(Row) do
    -- cannot be called without migration proof
    ...
  end
end

Cap(Db.Migrated) is unforgeable; every claim below is compiler-enforced:

  • The only mint is mint_cap(), and mint_cap() is gated. (cap_narrow, which once could forge one, was retired with the IO capability values it narrowed.)
  • Only public (fn) functions of mod Db can mint_cap it: private (pfn) functions may pass it through but cannot construct one.
  • External code can pass it through, but cannot construct one, and no polymorphic launder through a nested unannotated helper can erase the cap type either.

Any module that accepts Cap(Db.Migrated) must declare needs Db.Migrated. Forgery is a compile error:

mod Sys do
  mod Db do
    proof cap Migrated
  end

  mod App do
    needs IO
    needs Db.Migrated

    -- ERROR: only public functions of `Db` can construct `Cap(Db.Migrated)`.
    -- `mint_cap` outside the declaring module is rejected (here, by Check 6,
    -- because the mint sits in the declared return position).
    fn bad() : Cap(Db.Migrated) do mint_cap() end

    -- OK: pass-through is allowed
    fn relay(m : Cap(Db.Migrated)) : Cap(Db.Migrated) do m end
  end
end

History (widening slice 6, 2026-07-08): earlier releases had two gaps here. The documented mint idiom did not typecheck (a bare () at the end of a Cap(Db.Migrated)-returning body was rejected expected Cap(Db.Migrated) but got ()), and the mechanism that did work (cap_narrow, with a polymorphic return Cap(a) that instantiated to any proof cap at the call site) was unrestricted, so any holder of an ordinary Cap(IO) could mint any proof cap by name with no covering needs. Both are closed: the sanctioned mint is the gated mint_cap primitive, cap_narrow can no longer produce a proof cap in any position, and the nested-module type-erasure hole the deepest forge relied on (consume(id(cap)), laundering through a nested unannotated helper) is closed by the intra-module reference-soundness fix. See specs/lang/core-march-types.md §2.8.13 (proof-cap minting/forging/unforgeability) and §2.5.1 ((T-QualRef)) for the rule-numbered treatment and corpus witnesses. Since ocap phase 7b cap_narrow itself is retired, which closes the last residual forge route through it.

When to use proof caps

Proof caps suit ambient, payload-independent facts: things true about the system, not about a specific value:

Proof cap Meaning
Cap(Db.Migrated) Database migrations have run
Cap(Auth.Authenticated) The current request has a verified identity
Cap(App.Initialized) Application startup has completed
Cap(Config.Loaded) Configuration has been validated

The key test: is there a single, well-defined place in the codebase that produces this capability? If yes, a proof cap works cleanly. If initialization is diffuse, conditional, or happens in multiple places, a proof cap will feel awkward. Use a runtime flag instead.

When not to use proof caps

Don’t use proof caps for per-value facts. If the guarantee must be tied to a specific value (“this String has been sanitized”), use an opaque refined type:

mod Sanitize do
  ptype Sanitized = Sanitized(String)   -- private constructor

  fn sanitize(raw : String) : Sanitized do
    Sanitized(escape_html(raw))
  end

  fn render(s : Sanitized) : String do
    let (Sanitized(text)) = s
    text
  end
end

A Cap(Sanitized) would prove “some string was sanitized somewhere,” but not that the string you are about to render is the one that was sanitized. The opaque type ties proof and data together: you physically cannot pass an unsanitized string to render.

Don’t use proof caps when there’s no single mint point. Unforgeability is only meaningful when the minting surface is small and auditable. If the initialization is spread across many code paths, the cap gives a false sense of safety.

Typestate: tracking resource lifecycle

IO caps answer “is this module allowed to open a file?” Typestate answers “is this specific handle currently open or closed?” It builds on linear types: a handle is always_linear, so it must be used exactly once.

Handle(R, S) from the standard library

stdlib/handle.march ships a canonical typestate handle:

always_linear type Handle(r, s) = Handle(Int)

The r parameter is a phantom resource tag and s is the current state. Because Handle is always_linear, dropping it without consuming it, or consuming it twice, are both compile-time errors.

tag ConnTag
tag Closed
tag Open

fn connect() : Handle(ConnTag, Closed) needs IO.NetConnect do ... end
fn open(h : Handle(ConnTag, Closed)) : Handle(ConnTag, Open) do ... end
fn query(h : Handle(ConnTag, Open), sql : String) : (List(Row), Handle(ConnTag, Open)) do ... end
fn close(h : Handle(ConnTag, Open)) : Handle(ConnTag, Closed) do ... end

The wrong call order is a type error:

let h0 = connect(net_cap)
let h1 = query(h0, "SELECT 1")  -- ERROR: expected Handle(ConnTag, Open), got Handle(ConnTag, Closed)
let h2 = open(h0)               -- OK
let (rows, h3) = query(h2, "SELECT 1")
let h4 = close(h3)

Declaring transitions

A transitions block names every valid state transition. The compiler verifies each via function exists with the right signature, and warns about functions that look like transitions but are not declared:

mod Db do
  transitions Handle do
    ConnTag: Closed -> Open   via open
    ConnTag: Open   -> Closed via close
  end
end

always_linear type for your own handles

always_linear type FileHandle(s) = FileHandle(Int)

tag FileClosed
tag FileOpen

fn open_file(path : String) : FileHandle(FileClosed) do ... end
fn read_file(h : FileHandle(FileOpen)) : (String, FileHandle(FileOpen)) do ... end
fn close_file(h : FileHandle(FileOpen)) : FileHandle(FileClosed) do ... end

tag: zero-arg phantom label types

tag Foo is shorthand for type Foo = Foo: a zero-argument phantom type for state labels and resource tags:

tag ConnTag
tag Closed
tag Open

When to use typestate

Use typestate when:

  • A resource has a finite, well-defined lifecycle (closed → open → consumed)
  • Calling operations in the wrong order is a programmer error worth preventing statically
  • The resource must not be dropped without being explicitly released

Don’t use it for:

  • Simple flags or booleans that change frequently at runtime: the type parameter overhead is not worth it
  • Cases where the lifecycle state is dynamic and not known until runtime

The LSP shows typestate hover: hovering any Handle(R, S) expression displays the current state and all declared transitions from it.

Runtime dictionaries: swapping what a capability does

A capability proves permission. A dictionary attached to one also decides what the permitted operations do, so an implementation can be swapped at a binding site: for mocking in tests, for tracing, or for pointing a transport somewhere else.

Your own capabilities

Declare the dictionary type on the capability, then attach one:

mod Session do
  type Ops = { emit : (String) -> Int }
  proof cap Live with Ops
  needs IO

  fn boot() : Cap(Session.Live) do
    cap_impl(mint_cap(), { emit: fn s -> String.length(s) })
  end

  fn emit(c : Cap(Session.Live), s : String) : Int do
    match cap_dict(c) do
      Some(d) -> d.emit(s)
      None    -> String.length(s)   -- no dictionary: the ambient behaviour
    end
  end
end

cap_dict yields an Option, and None means “no dictionary: use the ambient implementation”. That is what every capability written before dictionaries existed reads as, which is why the default path stays visible in the source rather than being implied.

The dictionary type is monomorphic. proof cap Live with Ops names Ops with no type arguments, so a parameterised record (type Ops(m) = …) cannot be attached: the checker reports that Ops is declared with a type parameter but used with none. Give the varying part a concrete representation at the boundary instead. Session.Ops, the stdlib session transport, carries every message as Bytes for exactly this reason, which also keeps one dictionary type serving every protocol.

mint_cap() produces a new capability with no dictionary; attaching one is cap_impl’s job.

Who may attach one. Supplying a dictionary decides what a capability does, which is at least as much authority as minting one, so it is gated exactly like mint_cap: only a public fn of the declaring module, with the capability fixed at the call site. A supplier whose result type is left polymorphic is rejected, since it could re-implement every capability at once.

Mocking an IO capability in tests: mock

A test replaces what an IO capability does with a mock block:

mod GreeterTest do
  needs IO.Console

  test "the greeting is printed" do
    mock IO.Console with { print_line: Some(fn s -> assert(s == "hello, ada")) } do
      Greeter.greet("ada")
    end
    ()
  end
end

mock SCOPE with HANDLER do ... end is an expression with its body’s value. Inside the block, every interceptable operation of the scope’s capability kind whose target the scope admits goes to the handler instead of the outside world.

  • Test builds only. march test, forge test and any build with --test. Anywhere else a mock is the error mock_outside_test.
  • One kind per block. The scope is written literally and names one capability kind (IO.Console, IO.Clock, IO.FileRead("/fixtures/"), …); several kinds are nested blocks (mock_scope_invalid). A scoped mock covers only the targets its scope admits: under mock IO.FileRead("/fixtures/") a read of /fixtures/a.txt goes to the handler and a read elsewhere runs for real.
  • The handler is the kind’s operation record: one field per interceptable operation, each an Option that is None when the real operation should run. march --emit-io-ops prints every kind’s fields. A record literal in the with position names only the fields it overrides; the rest are None. A field the kind does not have is mock_handler_field. A zero-argument operation’s field takes () (unix_time_ms: Some(fn _ -> 0)), and an operation typed as a value holds the value (process_cwd: Some("/x")).
  • It travels like authority. A mock is a layer of the current authority (see Run-time authority), so a closure, task or actor created inside the block keeps the mock after the block ends, and a supervisor restart keeps it too. One created outside and called inside does not get it.
  • It admits what it covers. The block has authority for the operations its scope covers whether or not the test was launched with it. An operation it covers but whose field is None runs for real, checked against the authority outside the mock; a refusal there stops the test with a panic, so a mock never lets a test reach the outside world beyond its launch.
  • restrict still binds. A restrict inside a mock narrows as anywhere else: an operation it does not admit is refused, mocked or not.

Tables. mock IO.Mut("sessions", prefix("cache.")) with { open: None } do gives every table name the scope covers a private namespace for the life of the mock: the block (and what it creates) starts from an empty table, and the real table of that name is neither read nor written. The open field, when given, is asked by Vault.new, Vault.open, Vault.whereis, ns_get and ns_drop and can make the open fail: Some(fn name -> Err("down")) returns Err(CapError("IO.Mut", name, ByMock(_), "down")).

What cannot be intercepted

An operation that is not intercepted behaves exactly as it does outside a mock.

Not interceptable Why
println, random_bytes A program reaches these through a stdlib March function (Prelude.println, Crypto.random_bytes), not through the builtin; println is intercepted through the print_line it delegates to
The polymorphic vault_* operations one by one A record field would need rank-2 types; a vault mock instead isolates the table names it covers (above)
A builtin used as a value rather than called (List.map(paths, file_read)) The test build routes calls of an operation to its handler, not values of it

with_cap, and cap_impl / cap_ops_empty on an IO capability, were retired in favour of mock (ocap phase 7). cap_impl remains for a program’s own proof capabilities.

Advanced patterns

Specialization tags: realtime exclusion

Tagged(X, T) annotates a capability with a policy. The key narrowing rule: a function taking Tagged(_, Realtime) is in a realtime context and cannot also hold Alloc, IO or Panic, whether as a Cap(Alloc) parameter or by asking for it in a needs clause (fn f(t : Tagged(DSP, Realtime)) : () needs IO is refused too). The compiler rejects mixed signatures:

type DSP = DSP
type Realtime = Realtime

-- ERROR: realtime functions cannot take Cap(Alloc)
fn bad(cap : Tagged(DSP, Realtime), a : Cap(Alloc)) : () do () end

-- OK: statically proven — no allocation, no IO, no panic
fn process(cap : Tagged(DSP, Realtime), buf : Buffer(Float32, 256)) : Buffer(Float32, 256) do
  ...
end

Tagged also covers type-indexed specialization (SIMD widths, buffer sizes): monomorphization handles these for free:

fn fft(cap : Tagged(SIMD, N), buf : Buffer(Float32, N)) : Buffer(Complex32, N)
-- monomorphization produces fft_256, fft_1024, etc.

Handing out a narrow authority: records of functions

IO capabilities are not values (they were retired in object capabilities, phase 7b), so a function never receives its authority as an argument. To give a piece of code some authority and no more, hand it functions, and run it under restrict (): a function value keeps the authority of the place it was made (what keeps the narrowed authority), while the code you call is limited by the block.

type PluginEnv = { now : () -> Int, log : String -> () }

fn run_plugin(plugin : Plugin) : () needs IO.Clock, IO.Console do
  let env = { now: fn () -> System.now_ms(), log: fn s -> Authority.ignore(println(s)) }
  restrict () do
    plugin.run(env)   -- may read the clock and print through env, nothing else
  end
end

The record is the plugin’s whole authority: inside restrict () its own code can perform no capability operation, and the two closures carry run_plugin’s clock and console. A narrower record is a narrower plugin.

Testing with records of functions

The same record is the test seam when you want the swap to be visible in the signature: a LogEnv parameter says outright that the caller chooses the logger. Reach for mock instead when you want the swap to be invisible: code that prints can be mocked without changing its type.

type LogEnv = { write : String -> () }

test "process logs one line" do
  let lines = Vault.new("test_capture")
  Vault.set(lines, "n", 0)
  let env = { write: fn _ -> Vault.set(lines, "n", Option.unwrap_or(Vault.get(lines, "n"), 0) + 1) }
  let _ = process(env, test_input)
  assert(Vault.get(lines, "n") == Some(1))
end
